## Модель

Последовательная, без residual-связей. BatchNorm отсутствует: задание предписывает
после каждой свёртки только ReLU («After each convolution layer we use ReLU»,
раздел 3). Все свёртки с `padding = k // 2` и `bias=False`, все ReLU `inplace=True`,
вход `3 × S × S`, 100 классов на выходе.

18 слоёв, из них 17 порождают запуск CUDA-ядра (`Flatten` — это view), поэтому
$K = 17$. Параметров 1 040 324, то есть 3.97 МиБ весов в FP32.

## Сетка замеров

`SEED = 0`, 11 размеров изображения × 12 батчей = **132 конфигурации**.

* $S$: базовые 32, 64, 128, 224, 256, 384, 512 плюс случайные 80, 208, 304, 320
* $B$: базовые 1, 2, 4, 8, 16, 32, 64, 128, 256 плюс случайные 111, 133, 139

Валидационными считаются все конфигурации, где $S$ или $B$ взяты из случайной
добавки: **63 калибровочные / 69 валидационных** на T4. Калибровка θ использует
только калибровочные точки, все метрики качества считаются на валидационных.

## Формулы

$$\text{FLOPs}(S,B) = B\,(17751\,S^2 + 313\,956)$$

$$\text{Bytes}(S,B) = 364\,BS^2 + 8592\,B + 4\,161\,296$$

$$\text{Memory}(S,B) = 52\,BS^2 + 4\,161\,296\ \text{байт}$$

$$\text{Latency}(S,B,\theta) = K\,t_0 + \sum_{\ell=1}^{K}\max\!\Big(\frac{F_\ell}{V_c},\ \frac{M_\ell}{V_m}\Big)$$

$$\text{Energy}(S,B,\theta_E) = P_{idle}\cdot\text{Latency} + e_{flop}F + e_{byte}M$$

$\theta = (t_0,\ V_c,\ V_m)$ — секунды на запуск ядра, достигнутая арифметическая
пропускная способность, достигнутая пропускная способность памяти.

## Калибровка θ

Из трёх компонент θ подгоняется **одна**. Признаки $F$ и $M$ на этой сетке
коллинеарны: оба доминируются членом $BS^2$, отношение $F/M$ пробегает лишь
4.1…48.8, матрица признаков численно вырождена (cond ≈ 6.5·10⁴). Фит всех трёх
компонент сразу даёт малую ошибку при бессмысленной θ — один из параметров
уходит на границу области. Поэтому:

| θ | как получена |
|---|---|
| $t_0$ | измерена: минимум латентности по launch-углу ($BS^2 \le 2\cdot10^4$), делённый на $K$ |
| $V_m$ | измерена: микробенчмарк `copy_` на большом буфере, чистый memory-bound |
| $V_c$ | подогнана: одномерный поиск, задача монотонна по $V_c$ |

Для энергии так же: $P_{idle}$ измеряется отдельно (медиана мощности в простое),
подгоняется один коэффициент. $e_{byte}$ положен в ноль — раздельно с $e_{flop}$
он из этой сетки не извлекается по той же причине.

## Выводы

### Аномалия
Во время прогона модели, была обнаружена следующая аномалия. При батче примерно равным B=100 падала производительность. Было произведено исследование через профилирование. Обнаружено, что в процессе инференса, алгоритм свёртки выбирается эвристикой по форме тензона, без замеров. При B>64 эвристикой переключается с volta_scudnn на fft2d_r2c + volta_gcgemm + fft2d_c2r на одном слое Conv2d #0 (7×7 s2, 3→32).  Стоимость FFT-свёртки не зависит от размера ядра, поэтому для 7×7 она выглядит выгодной; эвристика не учитывает, что при $C_{in}=3$ полезной работы всего 147 MAC на выходной элемент. И это следствие `cudnn.benchmark = False` - с автотюнингом FFT был бы отброшен. Это так же объянсяет большую часть latency val MAPE. 


### Память
1. Отсутствуют OOM, т. к. Memory(512, 256) = 3.25 ГиБ против 14.6 ГиБ у T4.
2. Память систематически недооценена (см `parity.png`, `memory_vs_grid.png`, `error_map.png`). Объясняется это присутствием в памяти воркспейса cuDNN, которую изначально опусти.
3. Переход между *-bound режимами достигнут (см. `regimes.png`). Переход из memory-bound в compute-bound объясняется перевесом трафика активаций над трафиком весов модели. Далее потребление памяти продолжает расти, при этом, арифметика выходит в пик своих возможностей, т. к. все вычислители входят в работу.
4. `Memory активаций >> Memory весов модели`.
5. $\varepsilon_{compute}=45.9%$, $\varepsilon_{memory}=73.5$ от паспорта.

### Прогоны на GTX1050

Так как досигнуть OOM на T4 не удалось, я провел прогоны на [GTX1050](measure_GTX1050.ipynb). Артефакты в `results_GTX1050/`.

1. Удалось достигнуть OOM при S=512, B=256
2. Latency val MAPE: T4 — 25.7%, GTX 1050 — 6.4%, вчетверо лучше, чем на T4. Объясняется единым алгоритмом свёртки на всей сети из-за другой версии cuDNN и архитектуры Pascal.
